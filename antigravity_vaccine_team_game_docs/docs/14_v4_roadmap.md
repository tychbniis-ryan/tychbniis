# 14 第 4 版開發路線圖

## 版本定位

第 4 版以 `0.4.0-planning` 重新定位為「靜態 HTML5 優先、低 GAS 呼叫、免費方案穩定版」。

第 4 版不延續第 3 版的複雜即時互動方向，而是把課堂小遊戲調整成盡量由學員端與導師端靜態網頁完成顯示、作答、寶箱、成就與部分道具計算。GAS 只保留必要的遊戲啟動、資料載入、作答接收、挑戰卡結算、排行榜彙整與賽後報表。

## 第 4 版架構原則

1. 學員端與導師端皆以靜態 HTML5 網頁為主。
2. Firebase Hosting 只提供靜態頁面與靜態資源。
3. 遊戲開啟時由導師端觸發一次資料載入，包含題庫、答案、機率表與場次設定。
4. 學員登入時，前端依已載入的機率表與玩家識別資料，預先決定每一題是否取得寶箱、寶箱內容、成就寶箱內容。
5. 寶箱開啟不呼叫 GAS，不即時抽獎。
6. 成就判斷優先在學員端依題庫答案與本機作答紀錄計算。
7. 加倍卡與翻身卡盡量由學員端依規則計算後送出結果。
8. 挑戰卡因涉及戰隊間完成率，由 GAS 統一計算。
9. 移除創作題、隊內初選、匿名全體票選，降低免費方案下的流量與同步風險。
10. 暫不以防止惡意改封包為主要目標，但要避免網路延遲、重複點擊、重複送出造成分數錯誤。

## 第 4 版解決第 3 版未完成 BUG 與風險

### 問題

第 3 版已完成 `0.3.22` 定版，但仍保留下列現場風險：

1. 創作題與票選流程節點多，容易在 200 人同時操作時造成 Firebase 或 GAS 壓力。
2. 寶箱、成就與道具仍存在後端同步與前端即時狀態落差。
3. 關題關閉後，若大量學員同時更新摘要、道具或排行榜，仍有塞車風險。
4. GAS 同時計算剩餘秒數、題目得分、道具、排行榜時，免費方案下容易延遲。
5. 學員端重複點擊、網路重送、重新整理頁面，可能造成重複送答或 UI 狀態不一致。

### 第 4 版處理方式

1. 移除創作題與票選，直接降低最高風險互動流程。
2. 寶箱與成就改為學員端預先決定與本機計算，避免開箱與成就領取時呼叫後台。
3. 導師關題後開放 3 分鐘道具送出期，讓高峰流量分散。
4. 加倍卡與翻身卡結果由學員端先算好，GAS 只收結果並彙整。
5. 挑戰卡保留 GAS 計算，因為需要比較戰隊完成率。
6. 每位學員每題只允許建立一筆送答結果，前端用本機狀態鎖定，後端用 `playerId + questionId` 去重。
7. 前端對所有送出按鈕採用「送出中、已送出、不可再次送出」三段狀態。

## 遊戲資料讀取流程

### 1. 導師輸入密碼並開啟遊戲

導師端仍需輸入管理密碼。密碼只用於管理操作，不寫入前端程式或文件。

導師按「開啟遊戲」後，系統執行：

1. 載入題庫。
2. 載入正確答案。
3. 載入寶箱機率表。
4. 載入道具機率表。
5. 載入成就規則。
6. 載入戰隊設定。
7. 建立本場次 `gameSeed`，用於前端穩定產生預配寶箱。

注意：第 4 版為降低 GAS 呼叫，允許學員端取得答案並自行計算成就。這是課堂小遊戲的可接受風險；暫不處理惡意改封包作弊。

### 2. 學員登入

學員輸入暱稱後，前端建立或沿用：

1. `playerId`
2. `clientKey`
3. `teamId`
4. `gameSeed`

前端依 `gameSeed + playerId + questionId` 產生穩定結果：

1. 每 1 題是否獲得寶箱。
2. 該寶箱的道具內容。
3. 成就達成時取得的寶箱內容。

同一學員重新整理頁面時，預配結果必須一致，不可重新抽一次。

### 3. 題目作答

學員端從靜態題庫顯示題目。學員送出答案後，前端立即計算：

1. 是否答對。
2. 剩餘秒數。
3. 本題基本分。
4. 加倍卡個人加分。
5. 是否達成成就。
6. 是否取得預配寶箱。

送出資料給後端時，附帶前端已計算結果：

1. `playerId`
2. `questionId`
3. `answer`
4. `isCorrect`
5. `baseScore`
6. `bonusScore`
7. `finalQuestionScore`
8. `usedItemIds`
9. `clientSubmitId`

GAS 原則上不再重新計算剩餘秒數與基本分，只負責去重、接收、彙整與挑戰卡結算。

## 道具使用時間設計

### 規則

導師關閉題目後，開放 3 分鐘道具送出期。

在這 3 分鐘內：

1. 學員可自由送出本題關題後可使用的道具。
2. 前端顯示倒數。
3. 送出按鈕進入「送出中」後不可重複點擊。
4. 送出成功後顯示「已送出」。
5. 3 分鐘到期後，前端自動關閉道具送出入口。

在這 3 分鐘內，GAS 可在雲端接收資料並彙整計算，降低所有工作集中在關題瞬間。

### 道具計算分工

| 道具 | 計算位置 | 原因 |
|---|---|---|
| 加分卡 | 學員端先算，GAS 彙整 | 只影響本隊加分，可由前端送出結果 |
| 加倍卡 | 學員端先算，GAS 彙整 | 依下一題個人答對結果加個人分，不需後端即時計算秒數 |
| 翻身卡 | 學員端先判斷可用條件，GAS 彙整 | 第 4 版簡化為前端依公開排行榜或關題前狀態判斷 |
| 挑戰卡 | GAS 計算 | 需要比較戰隊間完成率，學員端無法可靠取得完整資料 |

## 第 4 版移除功能

第 4 版移除下列第 3 版功能：

1. 創作題投稿。
2. 隊內初選。
3. 講師審核代表作品。
4. 匿名全體票選。
5. 創作決選加分。

移除原因：

1. 免費方案下，創作題與票選會產生大量即時寫入與讀取。
2. 自由文字審核會增加現場操作負擔。
3. 課堂小遊戲的主要目標是互動與學習，不需要高風險同步流程。

## 重複送出與網路延遲防錯

### 前端防錯

1. 每次作答產生唯一 `clientSubmitId`。
2. 同一 `questionId` 送出後，選項與送出按鈕立即鎖定。
3. 若網路逾時，畫面顯示「送出確認中」，不可再次送出。
4. 若使用者重新整理頁面，前端從 `localStorage` 還原已送出狀態。
5. 道具送出同樣使用 `clientItemUseId` 去重。
6. 3 分鐘道具期結束後，不再允許送出新道具。

### 後端防錯

1. GAS 以 `gameId + questionId + playerId` 作答去重。
2. GAS 以 `gameId + itemId + playerId + questionId` 道具使用去重。
3. 已接收資料不因重送而加分兩次。
4. 重複請求回傳既有結果，不建立新紀錄。
5. GAS 不接收道具期結束後的新道具使用請求。

4. 規劃玩家登入時預配寶箱與道具內容。

## 第 4 版建議開發順序

1. `0.4.0-planning`：完成本路線圖修正。
2. `0.4.1`：整理第 3 版創作題與票選移除清單，標記前端、GAS、文件影響範圍。
3. `0.4.2`：設計靜態題庫、答案、機率表與成就規則資料格式。
4. `0.4.3`：重構學員端靜態計分、寶箱預配與成就計算。
5. `0.4.4`：重構導師端開啟遊戲與關題後 3 分鐘道具期。
6. `0.4.5`：調整 GAS，只保留接收結果、去重、挑戰卡、排行榜與報表。
7. `0.4.6`：回歸測試 200 人課堂操作流程。

## 第 4 版不做事項

1. 不啟用 Cloud Functions、Cloud Run、Blaze 或付費服務。
2. 不處理惡意改封包作弊，只處理正常使用下的重複送出與網路延遲。
3. 不保留創作題與票選。
4. 不把管理密碼、Token、Cookie、private key 或個資寫入程式或文件。
5. 不在未經確認時部署 GAS、Firebase Hosting、Firebase rules 或 Cloud Functions。

## 0.4.0-planning 完成範圍

Status：第 4 版規格已依使用者指定方向修正。

Root Cause：第 3 版功能完整但流程偏重後端同步，免費方案下仍有塞車風險；課堂小遊戲可接受較低防作弊等級，因此第 4 版改以靜態 HTML5 與前端預先計算為主。

Suggested Fix：後續先移除創作題與票選規格，再設計靜態資料格式，最後才進入前端與 GAS 的最小範圍重構。
